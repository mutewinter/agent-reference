# agent-reference.dev

The project site. [TanStack Start](https://tanstack.com/start) on a Cloudflare Worker, every route prerendered to HTML at build time.

```bash
pnpm install && pnpm dev
```

`pnpm build` writes `dist/`, `pnpm preview` serves that build, and `pnpm deploy` builds and pushes to Cloudflare.

This directory is its own project with its own lockfile, not a workspace package, the same arrangement `talks/` uses. The library's `files` allowlist in the root `package.json` is opt-in, so nothing here reaches the published tarball.

## Conventions

- **Prerendered, not server-rendered.** `tanstackStart({ prerender: { enabled: true } })` in [vite.config.ts](./vite.config.ts) crawls from `/` and writes an HTML file per route. The Worker is still deployed, because [src/worker.ts](./src/worker.ts) is what negotiates and what answers a wrong URL, but no page is rendered per request. Anything added here has to survive being generated at build time, including the build's own call into that Worker: prerendering asks it for every page before there is anything bound to serve, so every read of the assets binding falls back to a render.
- **The CLI's own visual language, framed in a text face.** Prose is Inter, terminal and file text is JetBrains Mono, and the two comparison headings use Oswald. The fonts load from Google Fonts with system fallbacks. Hairline rules and middle dots echo the CLI. Amber carries primary actions, green marks available source, and red marks opaque output. Within each example, matching references share an underline color and stroke pattern across transcripts, config, and folder trees. Path and commit aliases keep their reference's identity. Dark only, deliberately: a second palette is a second thing to keep honest.
- **No hashes on the page.** The store keys a checkout by commit, and a commit is not something a person reads, so every path the page shows names the repository and, for a package, the version: `~/.agent-reference/src/ai@7.0.78/packages/ai` rather than the literal path. The section about the store is the one place the real layout appears.
- **Setup is the primary action.** The centered Get started section holds `ForYourAgent` in [src/components/start.tsx](./src/components/start.tsx): selectable prompt text and a separate copy button in one card. The prompt is the copy payload; the surrounding explanation is excluded. The button spans the card on mobile, with no divider between the text and action. Manual installation stays visible beneath the card as a secondary option, with the install command and `agent-reference init` for the reader to run. Config panels retain their smaller copy controls. The setup prompt preserves its literal backticks because that is what the clipboard gets.
- **The first screen answers why, not how.** One comparison joins a subdued before pane to a brighter source pane, side by side on desktop and stacked on mobile. Each pane has one heading about the reader's agent; tool calls show opaque output in red and readable source in green. Opaque output is clipped to excerpts while source wraps in full. The left reads finish before the right heading reveals word by word, followed by the right reads and a quiet link to the TV ad the headings reference. Each pane waits until it enters view. The animation honors reduced motion and reserves the full transcript height. Two calls against three keep the comparison from reading as one fix per failure. One library throughout, Effect, because a reader recognizes it; every line on the right is quoted from the package at that tag, and the bundle line on the left stands for the pattern rather than for Effect's own build, which keeps its comments. What the tool is made of comes after the reader has a reason to care, in the order a first visit asks: the one prompt to copy, the config the agent keeps and reaches for, and only then the store, the format, and the commands. See [the decision](../docs/decisions/2026-09-01-the-page-answers-why-before-how.md) before reordering it.
- **Snippets are highlighted in Node, at build time.** They live in [code-samples.ts](./code-samples.ts) and a plugin in [vite.config.ts](./vite.config.ts) runs Shiki over them and serves the HTML as `virtual:highlighted`. Shiki never reaches the browser or the Worker, which is the point: a prerendered page has nothing to highlight at runtime.
- **The stylesheet is the design system, and `pnpm lint` enforces it.** [.oxlintrc.json](./.oxlintrc.json) points `oxlint-tailwindcss` at [src/styles.css](./src/styles.css), so every class on the page is resolved against the tokens declared in `@theme`: `no-arbitrary-value` rejects a size or a color written into a class, and a misspelled class is an unknown class rather than a rule that silently does nothing. A new size belongs in `@theme` under a name. `1fr auto 1fr` and its kind are the one exception, because a grid track list is a layout rather than a token.
- **`pnpm check-types` is the only thing that typechecks.** `vite build` does not. The `.mjs` sample modules are in [tsconfig.json](./tsconfig.json) with `allowJs`, so TypeScript infers their shape from the literals instead of handing the page an `any`, which means a key in `examples` that no longer exists in `samples` is a type error rather than an empty panel.
- **One palette, taken from the syntax theme.** [jellybeans-plus.json](./jellybeans-plus.json) is Jellybeans+ by Simon Watts (MIT, vendored from `siwatts/jellybeans-theme-vscode` because a CI build cannot fetch it). Shiki highlights with it, and the tokens in [src/styles.css](./src/styles.css) are derived from the same file: panels use its editor background, body text its foreground, and the amber and green come from its own token colors. Changing the theme means changing both.
- **The link preview is drawn, not screenshotted.** [og.ts](./og.ts) renders `public/og.png` and `public/apple-touch-icon.png` with [Takumi](https://takumi.kane.tw), reading the tagline and comparison headings out of [code-samples.ts](./code-samples.ts) and the palette out of the `@theme` block in [src/styles.css](./src/styles.css). The card pairs opaque output with a readable API excerpt and uses the site's Inter, JetBrains Mono, and Oswald fonts. Run it by hand with `pnpm og` and commit the PNGs; it is deliberately not part of the build, because a deploy should not depend on a font download or a native renderer. Regenerate after changing the tagline, comparison headings, fonts, palette, or mark. The opening markdown comparison separates tool labels from language-tagged result blocks so GitHub can highlight the source without treating the harness transcript as code.
- **The version comes from the CLI.** `vite.config.ts` reads `version` out of the repository root `package.json` and defines `__CLI_VERSION__`, so the badge in the header cannot disagree with the package it links to.
- **This page is the source the README renders from, and the markdown too.** Every word the page says about itself lives in [code-samples.ts](./code-samples.ts): the tagline and meta description, the section headings, the examples, and the section copy. [page-markdown.ts](./page-markdown.ts) renders those, plus the transcripts from [cli-reference.ts](./cli-reference.ts), as markdown; `scripts/sync-readme.ts` pastes them into the marked regions of [the README](../README.md) and `scripts/sync-agent-files.ts` writes them to `public/index.md`. Tests fail when either is behind. Change the copy here and run `npm run sync-readme` and `npm run sync-agent-files` at the root. A new section on the page is a new heading in both, which is what the markdown test checks. The README's reference sections have no counterpart here.
- **The page has a second reader.** An agent that sends `Accept: text/markdown` to `/` gets `public/index.md` instead of the HTML, under `Vary: Accept`, and a URL that matches nothing answers in markdown rather than rendering the shell into a 404. Both decisions are made in [src/worker.ts](./src/worker.ts), which is why [wrangler.jsonc](./wrangler.jsonc) routes `/` to the Worker before the assets layer sees it; everything else is still served straight from assets. The negotiation itself is in [negotiate.ts](./negotiate.ts) and the strings it answers with are in [agent-responses.ts](./agent-responses.ts), both plain enough for the root test suite to import. See [the decision](../docs/decisions/2026-08-25-two-readers-one-url.md) before publishing another manifest: the catalogs and server cards those readiness checklists ask for describe services this project does not run.
- **Everything under `public/` that an agent reads is generated.** `index.md`, `llms.txt`, the schema copy, and the skill under both `.well-known/agent-skills/` and `.well-known/skills/` are all written by `scripts/sync-agent-files.ts` from the page copy, [skills/](../skills/), and [schema/](../schema/). Edit the source, not the copy. The skill is under two trees because the convention forked: the first is the Agent Skills Discovery RFC a readiness scanner grades, the second is what `npx skills add https://agent-reference.dev` actually reads. [public/_headers](./public/_headers) gives them their media types and opens CORS, because they are served by the assets layer rather than by the Worker and that is the only place to set a header on them.

## Deployment

Pushing to `main` builds and deploys through Workers Builds. Other branches build too and get a preview URL rather than production, which works here only because this Worker has no Durable Objects; Cloudflare does not generate preview URLs for Workers that do.

The Worker is `agent-reference-site` and serves `agent-reference.dev` as a custom domain, declared in [wrangler.jsonc](./wrangler.jsonc). The name there and the name in the Cloudflare dashboard have to match or every build fails.

The build renders the CLI reference by running the CLI out of the repository root, and that CLI imports its own dependencies. A build installs this directory's lockfile and nothing else, which leaves the root without `node_modules` and the first command failing to resolve `semver`, so `pnpm build` runs [cli-deps.mjs](./cli-deps.mjs) first: it installs the root's runtime dependencies when they are not already resolvable, and on a machine that has installed the root it does nothing.

`public/talk/` is the NashJS deck, built out of `talks/2026-08-25-nashjs` by `pnpm talk:build` at the repository root and committed. Vite copies `public/` verbatim, so it ships with the site and needs nothing on the build. Re-run that command after changing the slides; nothing here notices that they moved.

## Gotchas

- `allowBuilds` in [pnpm-workspace.yaml](./pnpm-workspace.yaml) is a map of name to boolean, not a list. A YAML sequence is silently rewritten to keys `'0'`, `'1'` and matches nothing, so the install keeps failing with `ERR_PNPM_IGNORED_BUILDS` while the setting looks present.
- Route components are prerendered, so anything reaching for `window` has to do it in an effect or an event handler.
- [public/sitemap.xml](./public/sitemap.xml) lists routes by hand, because there is one. A second route means a second entry there, and the canonical URLs it and [src/routes/__root.tsx](./src/routes/__root.tsx) carry have no trailing slash, matching the `html_handling` in [wrangler.jsonc](./wrangler.jsonc).
